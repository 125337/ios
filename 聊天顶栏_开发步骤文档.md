> **本次核心原则**：百分百复制微信优化（123456.c），123456.c 没有的我们一概不加。
>
> 三个问题根因：
> 1. **头像顶栏消失** → `object_getClass(self) != baseCls` 过滤掉了所有 WeChat 子类实例

## 一、三个问题的精确定位

### 1.1 头像顶栏完全消失 — 根因 `object_getClass` 精确匹配

#### 问题表现

`plugin(56).log` 日志证据（L161-163）：
```
[HideAvatar] viewDidLoad triggered
[HideAvatar] updateChatContext: username=48551701903@chatroom chatType=2
[HideAvatar] viewDidLoad triggered
[HideAvatar] updateChatContext: username=wxid_duh359s6qbjn22 chatType=1
```

HideAvatar 的 hook_viewDidLoad **正常触发**，但 ChatTopBar 的 hook_viewDidLoad **完全没有日志输出**。

#### 根因：`ChatTopBarHook.m` L48-49 和 L91-92

```objc
// ChatTopBarHook.m L48-49（当前代码 — 错误！）
Class baseCls = objc_getClass("BaseMsgContentViewController");
if (object_getClass(self) != baseCls) return;  // ← 过滤了所有子类实例
```

**为什么错误**：微信内部不使用 `BaseMsgContentViewController` 本身作为实例类。真正进入聊天页时，`self` 的实际类是 `BaseMsgContentViewController` 的某个**子类**（微信运行时动态创建或内部子类化）。`object_getClass(self)` 返回的是子类的 Class 对象，`!= baseCls` 导致 **100% 的调用被过滤掉**。

#### 123456.c 的精确做法

123456.c 对 BaseMsgContentViewController 的 hook **不做任何 class 过滤**。以 HideAvatar 模块为例（123456.c 中对应的是同一个 dylib 内的其他 hook）：

```
// 123456.c L34370-34372
uVar1 = _objc_getClass("BaseMsgContentViewController");
_MSHookMessageEx(uVar1, "init", FUN_0003b200, &DAT_0013ad88);
_MSHookMessageEx(uVar1, "tableView:cellForRowAtIndexPath:", FUN_0003b270, &DAT_0013ad90);
```

hook 函数内部**不检查 `object_getClass(self)`**，直接执行业务逻辑。所有实例（含子类）都会进入 hook。

#### 精确修复

**ChatTopBarHook.m**：**删除** L47-49 和 L90-92 的 `object_getClass` 检查。

```objc
// ========== hook_viewDidLoad（修复后）==========

#### Crash 证据

```

#### 深度排查：我们在 CSChatAvatarTitleView.m 中找到了三个 123456.c 根本没有的代码

逐一比对 123456.c 的完整反编译，搜索关键词：

| 搜索词 | 123456.c 出现次数 | 我们代码 |
|--------|-----------------|---------|
| `silentLoadContactExtInfo` / preload | **0 次** | `CSChatAvatarTitleView.m` L286-309 |
| `dispatch_after` 创建 ContactInfoViewController 并 dismiss | **0 次** | `CSChatAvatarTitleView.m` L301-308 |
| `dispatch_async(main_queue, ^{ set image })` | **0 次**（在顶栏上下文中） | `CSChatAvatarTitleView.m` L376-382 |

123456.c 中 `ContactInfoViewController` 只出现在 `handleProfileNavigation_`（用户主动点击后跳转），**从不预先创建、预加载、或异步 dismiss**。

---

#### 可疑代码 #1（最可能的根因）：`silentLoadContactExtInfo` 预加载

```objc
// CSChatAvatarTitleView.m L286-309
- (void)silentLoadContactExtInfo:(id)contact {
    Class infoVCClass = objc_getClass("ContactInfoViewController");
    // ...
    id infoVC = [[ContactInfoViewController alloc] init];
    [infoVC setM_contact:contact];              // 设值
    ((void (*)(id, SEL))objc_msgSend)(infoVC, @selector(view));  // 强制加载 view！

    dispatch_after(0.8秒, main_queue, ^{
        [infoVC dismissViewControllerAnimated:NO completion:nil];  // ← 从未 present 的 VC 上调用 dismiss！
        [infoVC release];
    });
}
```

**致命问题**：

1. **对从未 present 的 VC 调用 dismiss**：`dismissViewControllerAnimated:completion:` 期望 dismiss 一个已经 present 的 VC。对未 present 的 VC 调用 dismiss 是**未定义行为**，可能触发 UIKit 内部 inconsistent 状态。
2. **强制 `[infoVC view]` 加载 ContactInfoViewController 的完整视图树**：ContactInfoViewController 内部包含 WCTableView（微信自定义 TableView）、大量数据查询。这个加载过程会：
   - 访问 `MMServiceCenter`、`CContactMgr` 等全局服务
   - 可能触发数据库查询
   - 创建 WCTableView 并初始化其 dataSource/delegate
3. **调用时机**：`silentLoadContactExtInfo` 在 `updateAvatars`（L323）中调用，而 `updateAvatars` 在 `viewWillAppear` hook 中调用（ChatTopBarHook.m L137）。这意味着**每次进入聊天页都会创建并销毁一个 ContactInfoViewController**。
4. **闪退链路推断**：
   ```
   进入聊天页 → viewWillAppear → updateAvatars → silentLoadContactExtInfo
     → 创建 ContactInfoViewController → 强制 [view] 触发 viewDidLoad
       → ContactInfoVC 内部创建 WCTableView、查询数据
       → 修改 CContactMgr / MMServiceCenter 全局状态
   
   用户返回会话列表、滑动
     → NewMainFrameViewController 的 tableView 更新 cells
       → 访问被 ContactInfoVC 修改过的共享数据
   
   0.8 秒后 → dispatch_after 触发
     → [infoVC dismissViewControllerAnimated:...]  ← 从未 present，UIKit 状态异常
       → UIKit 尝试更新 presenting VC 的视图状态
         → 写入已释放或无效的视图数据 → EXC_BAD_ACCESS at 0x54
   ```

---

#### 可疑代码 #2：`updateAvatars` 中的 `dispatch_async(main_queue, ^{...})`

```objc
// CSChatAvatarTitleView.m L376-382
dispatch_async(dispatch_get_main_queue(), ^{
    self.leftAvatarView.image = displayOpponent;   // ← 异步设置 image
    self.rightAvatarView.image = displaySelf;
    self.titleLabel.text = titleText;
});
```

**问题**：block 强引用 `self`（MRC 下 block 拷贝时 retain），但 block 执行时 CSChatAvatarTitleView 可能正在进行 dealloc。设置 `image` 会触发 UIImageView 的 layout 更新，在 dealloc 期间的 layout 可能导致访问已释放的子视图。

---

#### 可疑代码 #3：`chatController` 属性为 `assign`

```objc
// CSChatAvatarTitleView.h L7
@property (nonatomic, assign) BaseMsgContentViewController *chatController;
```

**问题**：`assign` 不 retain。当 BaseMsgContentViewController 被 pop 出导航栈释放后，`chatController` 变成悬空指针。CSChatAvatarTitleView 作为 `navigationItem.titleView` 可能比 VC 活得更久（导航栏转场动画期间），任何对 `self.chatController` 的访问（layoutSubviews、tap 手势）都会 crash。

123456.c 中的等效实现不暴露这个问题，因为它的 titleView 生命周期与 VC 严格绑定。

---

#### 修复方案（三管齐下）

**修复 #1：完全删除 `silentLoadContactExtInfo` 方法和调用**

123456.c 没有任何预加载逻辑，直接删除。

```
删除 CSChatAvatarTitleView.m L286-309（整个 silentLoadContactExtInfo 方法）
删除 CSChatAvatarTitleView.m L323（[self silentLoadContactExtInfo:contact] 调用）
```

**修复 #2：把 `dispatch_async` 改成同步执行**

123456.c 所有 UI 操作都是同步的，不异步。

```objc
// 改前（L376-382）：
dispatch_async(dispatch_get_main_queue(), ^{
    self.leftAvatarView.image = displayOpponent;
    self.rightAvatarView.image = displaySelf;
    self.titleLabel.text = titleText;
});

// 改后：直接同步执行（已在主线程）
self.leftAvatarView.image = displayOpponent ?: [UIImage imageNamed:@"DefaultHead"];
self.rightAvatarView.image = displaySelf ?: [UIImage imageNamed:@"DefaultHead"];
self.titleLabel.text = titleText;
```

**修复 #3：`chatController` assign → 添加 dealloc 防护**

属性声明改为 `assign` 是合理的（避免循环引用），但需要在 CSChatAvatarTitleView 的 `dealloc` 中主动置空引用，并且所有使用处加 nil 检查（当前已有 `if (!self.chatController) return`）。

不需要改属性类型，但确保在 BaseMsgContentViewController 释放时（`viewDidDisappear` 或 `dealloc`），不再有对 `chatController` 的异步访问。

- (void)onHomepageTapped {

    Class infoVC = objc_getClass("ContactInfoViewController");
    if (!infoVC) return;

    // 123456.c L118384: [[ContactInfoViewController alloc] init]
    id vc = ((id (*)(Class, SEL))objc_msgSend)(infoVC, NSSelectorFromString(@"alloc"));
    vc = ((id (*)(id, SEL))objc_msgSend)(vc, NSSelectorFromString(@"init"));

    // 123456.c L118386: [vc setValue:contact forKey:@"m_contact"]
    // ★ 不包 @try/@catch，123456.c 没有任何异常处理
    ((void (*)(id, SEL, id, NSString *))objc_msgSend)(vc,
        NSSelectorFromString(@"setValue:forKey:"), self.contact, @"m_contact");

    [vc retain];

    // 123456.c L118395: [self dismissViewControllerAnimated:YES completion:block]
    [self dismissViewControllerAnimated:YES completion:^{
        // 123456.c L118418-118421: [weakSelf presentingViewController]

        if (!presenting) { [vc release]; return; }

## 五、MRC 内存管理要点

1. **关联对象用 `OBJC_ASSOCIATION_RETAIN_NONATOMIC`**：已在第十六版修复，宿主 dealloc 时自动 release 持有的 titleView，无野指针
2. **Block 手动 retain vc**：123456.c L118393 `_objc_retain(vc)` → 我们的 `[vc retain]`，block 结束 `[vc release]`
3. **`objc_getAssociatedObject` 返回的对象**：在 MRC 下是 autoreleased 还是 +0 取决于关联策略。RETAIN 策略下是 +0（不 retain），只需在宿主存活期间使用，不需要额外 retain/release
4. **CSChatAvatarTitleView 的 alloc/init**：`viewDidLoad` 中 `alloc init` → `[view release]`（setTitleView 会 retain），`viewWillAppear` 中同理
