## 一、三个问题逐一定位（与 123456.c 精确对比）

### 1.1 会话列表页上下滑动闪退

#### 123456.c 中的 hook（L30218-30220）

```c
uVar1 = _objc_getClass("NewMainFrameViewController");
_MSHookMessageEx(uVar1, "tableView:cellForRowAtIndexPath:", FUN_000323f0, &DAT_0013ad20);
```

**事实**：微信优化 1.6.5 **直接 hook 了会话列表页 `NewMainFrameViewController`** 的 `tableView:cellForRowAtIndexPath:` 方法。`FUN_000323f0` 是替换实现，在 cell 创建/复用过程中操作 `_sections` 等内部数据结构。

#### 项目的影响路径

`ChatTopBarHook.m` L63：
```objc
objc_setAssociatedObject(self, kOriginalTitleViewKey,
                         (__bridge id)(void *)originalTitleView,
                         OBJC_ASSOCIATION_ASSIGN);   // ← MRC 下危险的 assign
```

`OBJC_ASSOCIATION_ASSIGN` 等同于 `__unsafe_unretained`。当 `BaseMsgContentViewController` 被 pop 出导航栈后释放时，关联的 `originalTitleView` 变成野指针。后续任何通过 `kOriginalTitleViewKey` 访问该指针的操作都会访问已释放的内存。

同时，`ChatTopBarHook.m` L46-49 的 `isKindOfClass` 检查实际上是**无效的**：因为 hook 本身就安装在 `BaseMsgContentViewController` 类上，`self` 永远是 `BaseMsgContentViewController` 或其子类，`isKindOfClass` 永远返回 YES，无法过滤掉会话列表页触发的调用。

#### 冲突链路（两个插件叠加）

```
用户滑动会话列表
  → NewMainFrameViewController::tableView:cellForRowAtIndexPath: 被调用
    → 微信优化 hook (FUN_000323f0) 执行，操作 cell 数据
    
    同时，如果会话列表中有预加载的 BaseMsgContentViewController 实例
    → viewWillAppear: 被调用
      → ChatTopBarHook 的 hook_viewWillAppear 执行
        → 访问 objc_getAssociatedObject(self, kOriginalTitleViewKey)
          → 如果 self 是已释放后重建的实例，此指针可能是垃圾值
          
  → 微信优化的 cell hook 访问 _sections / cell 内部属性
    → 如果内存已被其他操作污染 → EXC_BAD_ACCESS at 0x54
```

#### 解决方案

**1）将 `OBJC_ASSOCIATION_ASSIGN` 改为 `OBJC_ASSOCIATION_RETAIN_NONATOMIC`**

`ChatTopBarHook.m` L61-64：
```objc
// 改前：
objc_setAssociatedObject(self, kOriginalTitleViewKey,
                         (__bridge id)(void *)originalTitleView,
                         OBJC_ASSOCIATION_ASSIGN);

// 改后：
objc_setAssociatedObject(self, kOriginalTitleViewKey,
                         originalTitleView,
                         OBJC_ASSOCIATION_RETAIN_NONATOMIC);
```

关联对象会在 `self` 释放时自动 release 持有的 `originalTitleView`，不会产生野指针。

**2）移除无效的 isKindOfClass 检查**

当前 L46-49 的检查是冗余的，改为检查具体的 `NSStringFromClass` 以确保只在聊天页执行：
```objc
static void hook_viewDidLoad(id self, SEL _cmd) {
    ((void (*)(id, SEL))_orig_BaseMsgContentVC_viewDidLoad)(self, _cmd);

    // ★ 只在 BaseMsgContentViewController 本身（非子类）执行
    Class baseCls = objc_getClass("BaseMsgContentViewController");
    if (object_getClass(self) != baseCls) return;
    // ... 后续代码
}
```

**3）如果用户同时使用了微信优化 1.6.5**

建议在 `ChatTopBarHook.m` 的 `install` 方法中检测是否加载了微信优化，并在 P1 优先级输出日志提示冲突风险。

### 1.2 弹窗可以左右滑动（微信优化只能上下滑动）

#### 123456.c 的配置（L116659-116663）

```c
// UITableView initWithFrame:self.view.bounds style:2 (Grouped)
uVar1 = FUN_000c65c0(uVar1, extraout_x1, 2);

// autoresizingMask = 0x2 = UIViewAutoresizingFlexibleWidth（仅宽度！）
FUN_000ce300(*(undefined8 *)(param_1 + lVar4), 0x2);
```

#### 项目当前配置（CSContactInfoPopoverController.m L77-79）

```objc
UITableView *tableView = [[UITableView alloc] initWithFrame:self.view.bounds
                                                      style:UITableViewStyleGrouped];
tableView.autoresizingMask = UIViewAutoresizingFlexibleWidth | UIViewAutoresizingFlexibleHeight;
//                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                            两个方向都自动伸缩 (值 18)，123456.c 只用 FlexibleWidth (值 2)
```

#### 差异分析

`autoresizingMask = UIViewAutoresizingFlexibleWidth | UIViewAutoresizingFlexibleHeight` 允许 tableView **同时在宽和高两个方向跟随父视图伸缩**。在 popover 场景中：

1. `viewDidLoad` 时 `self.view.bounds` 是全屏宽度（~390pt），tableView 初始宽度 = 390
2. Popover 布局后视图缩小到 272pt，tableView 宽度变为 272
3. 但 tableView 作为 UIScrollView 子类，`contentSize` 可能保持为初始布局的宽度
4. `contentSize.width > bounds.size.width` → 允许水平滚动

而 123456.c 只用 `FlexibleWidth`（值 2），高度固定，不会触发双向伸缩导致的 contentSize 异常。

#### 精确修复

`CSContactInfoPopoverController.m` L79：
```objc
// 改前：
tableView.autoresizingMask = UIViewAutoresizingFlexibleWidth | UIViewAutoresizingFlexibleHeight;

// 改后（与 123456.c L116662 一致：仅 FlexibleWidth = 0x2）：
tableView.autoresizingMask = UIViewAutoresizingFlexibleWidth;
```

同时显式禁用水平方向：
```objc
// 添加在 L94 (showsVerticalScrollIndicator = NO) 之后：
tableView.alwaysBounceHorizontal = NO;
tableView.showsHorizontalScrollIndicator = NO;
```

#### 项目当前实现与 123456.c 的差异

| 步骤 | 123456.c | 项目当前 | 问题 |
|------|----------|---------|------|
| 获取 contact | 从 `item` 关联对象 `"profileContact"` 取 | 直接用 `self.contact` | 等效，OK |
| 设置 contact | `FUN_000ce560` = `setValue:forKey:` | 同样的 KVC `setValue:forKey:@"m_contact"` | **key 可能不匹配当前微信版本** |
| Block 捕获 self | `_objc_initWeak` + `_objc_copyWeak`（weak） | MRC 原始指针（`__unsafe_unretained`） | dismiss 后 self 可能失效 |
| Block 捕获 vc | `_objc_retain` 强引用 | 原始指针 | MRC 下 block 不自动 retain |
| 失败处理 | nav=nil → modal present | 无 → 静默失败 | **用户看到"没反应"的根因** |

#### 主页跳转无反应的三个可能根因

**根因 A（最可能）**：KVC key `@"m_contact"` 在当前微信版本中**不是有效的 KVC key**。

`setValue:forKey:` 查找 ivar 的顺序：`_m_contact` → `_isM_contact` → `m_contact` → `isM_contact`。

如果 ContactInfoViewController 的 ivar 名称是 `_contact`（纯 `_` 前缀），则 key `@"m_contact"` 找不到，抛出 `NSUndefinedKeyException`。WeChat 有全局异常处理器，静默捕获后**看起来就像"没反应"**。

**验证方法**：在 `onHomepageTapped` 中加 `@try/@catch`，catch 中用 `object_setIvar` + class_getInstanceVariable 直接设 ivar。

**根因 B**：MRC 下 block 不自动 retain `vc`。

123456.c 的 `_objc_retain(uVar6)` 在 block 创建时 retain 了 ContactInfoVC。我们的 MRC block 不 retain，dismiss 动画期间 vc 可能被释放。

**根因 C**：`self.presentingViewController` 类型不匹配。

123456.c 的 block 中先检查 `isKindOfClass:[UINavigationController]`，再回退到 `.navigationController`，最后还有 modal present 兜底。我们的代码假设 `.navigationController` 总是存在，没有兜底。

#### 精确修复

```objc
- (void)onHomepageTapped {
    // 123456.c L118375: objc_getClass("ContactInfoViewController")
    Class infoVC = objc_getClass("ContactInfoViewController");
    if (!infoVC) {
        infoVC = objc_getClass("WCContactInfoViewController");
    }
    if (!infoVC) {
        UIAlertController *alert = [UIAlertController
            alertControllerWithTitle:nil
            message:@"当前微信版本不支持直接跳转资料页"
            preferredStyle:UIAlertControllerStyleAlert];
        [alert addAction:[UIAlertAction actionWithTitle:@"确定"
                                                  style:UIAlertActionStyleDefault
                                                handler:nil]];
        [self presentViewController:alert animated:YES completion:nil];
        return;
    }

    // 123456.c L118383-118386: alloc init + KVC
    id vc = ((id (*)(Class, SEL))objc_msgSend)(infoVC, NSSelectorFromString(@"alloc"));
    vc = ((id (*)(id, SEL))objc_msgSend)(vc, NSSelectorFromString(@"init"));
    if (!vc) return;

    // ★ 123456.c L118386: setValue:forKey:@"m_contact"
    // ★ 用 @try/@catch 防止 key 不存在时静默失败
    BOOL contactSet = NO;
    @try {
        ((void (*)(id, SEL, id, NSString *))objc_msgSend)(vc,
            NSSelectorFromString(@"setValue:forKey:"), self.contact, @"m_contact");
        contactSet = YES;
    } @catch (NSException *e) {
        // KVC key "m_contact" 不存在 → 尝试直接设 ivar
        Ivar ivar = class_getInstanceVariable(infoVC, "m_contact");
        if (!ivar) ivar = class_getInstanceVariable(infoVC, "_m_contact");
        if (!ivar) ivar = class_getInstanceVariable(infoVC, "_contact");
        if (ivar) {
            object_setIvar(vc, ivar, self.contact);
            contactSet = YES;
        }
    }
    if (!contactSet) {
        [vc release];
        UIAlertController *alert = [UIAlertController
            alertControllerWithTitle:nil
            message:@"无法设置联系人信息，请更新插件"
            preferredStyle:UIAlertControllerStyleAlert];
        [alert addAction:[UIAlertAction actionWithTitle:@"确定"
                                                  style:UIAlertActionStyleDefault handler:nil]];
        [self presentViewController:alert animated:YES completion:nil];
        return;
    }

    // ★ 123456.c L118387-118395：MRC 下需手动 retain vc 供 block 使用
    [vc retain];

    // 123456.c L118395: dismiss + completion block
    [self dismissViewControllerAnimated:YES completion:^{
        // 123456.c L118418-118421: [weakSelf presentingViewController]
        UIViewController *presenting = self.presentingViewController;
        if (!presenting) { [vc release]; return; }

        // 123456.c L118422-118431: 先判断 presentingVC 是否就是 nav
        UINavigationController *nav = nil;
        if ([presenting isKindOfClass:[UINavigationController class]]) {
            nav = (UINavigationController *)presenting;
        } else {
            nav = presenting.navigationController;
        }

        // 123456.c L118432-118437: nav 不存在 → modal present 兜底
        if (nav) {
            [nav pushViewController:vc animated:YES];
        } else {
            [presenting presentViewController:vc animated:YES completion:nil];
        }
        [vc release];
    }];
}
```

## 六、MRC 注意事项

1. **Block 不自动 retain 捕获对象**：`dismissViewControllerAnimated:completion:` 的 block 中使用的 `vc` 和 `self` 不会被 block retain。必须在 block 创建前手动 `[vc retain]`，在 block 中 `[vc release]`
2. **`object_setIvar` 在 MRC 下正常**：`object_setIvar` 自动 retain 新值并 release 旧值（如果 ivar 是 retain 属性），不需要手动管理
3. **`@try/@catch` 异常处理**：MRC 下异常处理正常工作，但异常跳出时栈上的对象不会自动 release。`onHomepageTapped` 的 try/catch 作用域内只有 `vc` 一个需要管理的对象，catch 中已处理
4. **`OBJC_ASSOCIATION_RETAIN_NONATOMIC`**：关联对象在宿主（BaseMsgContentViewController）释放时自动 release 持有的 titleView，彻底消除野指针
