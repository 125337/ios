## 每个 Cell/ViewModel 5 连 Hook

每个目标类 hook **5 个方法**，形成完整隐藏链：

| 方法 | 所属 | 功能开启时行为 | 作用 |
|------|------|--------------|------|
| `initWithViewModel:` | Cell | setHidden:YES + setFrame: | 创建时标记隐藏，触发父类 `[super initWithViewModel:]` |
| `layoutInternal` | Cell | 直接 return（跳过） | 阻止布局计算 |
| `canBeReused` | Cell | 返回 YES | 标记 Cell 可立即复用 |
| `shouldLayoutIfNeeded` | Cell | 返回 NO | 告知 TableView 不需要重新布局 |
| `measure:` | ViewModel | 返回 CGSizeZero | 返回零高度给 TableView |

### Hook 函数逻辑（对齐微信优化 1.6.5）

```objc
// initWithViewModel: — 对齐 FUN_00025c48/5f64
static id hook_XxxCell_initWithViewModel(id self, SEL _cmd, id viewModel) {
    id result = _orig(self, _cmd, viewModel);     // 先调用原始初始化
    if (result && purifyReadConfig(@"ConfigKey")) {
        [result setHidden:YES];                    // 隐藏 Cell View
        [result setFrame:[result frame]];          // getFrame→setFrame，触发 setNeedsLayout
    }
    return result;
}

// layoutInternal — 对齐 FUN_00025d18/6034
static void hook_XxxCell_layoutInternal(id self, SEL _cmd) {
    if (purifyReadConfig(@"ConfigKey")) return;    // 跳过布局
    _orig(self, _cmd);
}

// canBeReused — 对齐 FUN_00025d94/60b0
static BOOL hook_XxxCell_canBeReused(id self, SEL _cmd) {
    if (purifyReadConfig(@"ConfigKey")) return YES; // 可复用
    return _orig(self, _cmd);
}

// shouldLayoutIfNeeded — 对齐 FUN_00025e24/6140
static BOOL hook_XxxCell_shouldLayoutIfNeeded(id self, SEL _cmd) {
    if (purifyReadConfig(@"ConfigKey")) return NO;  // 不需要布局
    return _orig(self, _cmd);
}

// measure: — 对齐 FUN_00025eb4/61d0
static CGSize hook_XxxVM_measure(id self, SEL _cmd, CGSize size) {
    if (purifyReadConfig(@"ConfigKey")) return CGSizeZero; // 零高度
    return _orig(self, _cmd, size);
}
```

> **注意**: `setHidden:YES` 后必须调用 `[result setFrame:[result frame]]`（getFrame → setFrame）。
> 微信优化反编译 FUN_00025c48 L23097-23099 明确包含这三个调用。不能省略 setFrame。

## 核心难题：交叉污染

### 问题本质

当对**父子类**同时 hook 同一方法时，子类 `_orig` 可能指向父类的 hook（而非原始 IMP），形成：

```
Pat hook → Sys hook → 原始     ← 坏链（_orig 指向了父类 Hook）
Pat hook → 原始 AppPat IMP    ← 好链（_orig 指向子类自身 IMP）
```

### 触发条件

`MSHookMessageEx(cls, sel, hook, &_orig)` 的内部实现：
1. `class_getInstanceMethod(cls, sel)` 在当前类的方法表中查找
2. 如果**未找到**（子类未覆写，继承自父类）→ 沿继承链遍历
3. 如果父类已被 hook（安装顺序 Sys→Pat）→ 返回的是**父类 hook 的 IMP**
4. `_orig` = 父类 hook → 形成交叉污染链

### 微信优化为什么安全

微信优化全部使用直接 `MSHookMessageEx`（FUN_00025688），没有 class_addMethod 预处理。它安全的原因：

- **微信优化目标版本的微信中**，`AppPatMessageCellView` 覆写了全部 5 个方法
- 子类覆写时，`class_getInstanceMethod` 在子类方法表中直接找到 → `_orig` = 子类自己的 IMP → 安全

### 我们的版本为什么出问题

微信版本不同，类的内部实现也不同。我们的微信版本中 `AppPatMessageCellView` 未必覆写全部方法。

另有 [`TintHook.m`](../WeChatPlugin/Modules/Layout/TintHook.m) 用 `method_setImplementation` 直接修改了 `BaseMessageCellView` 的 `updateStatus`/`layoutContentView`。这进一步污染了继承链，导致 `MSHookMessageEx` 的 `class_getMethodImplementation` 在遍历到 Base 层时捕获到不正确的 IMP。

## 解决方案：purifySafeHook

### 机制

```objc
// 1. 运行时检测：子类是否覆写了该方法？
static BOOL purifyIsOverridden(Class cls, SEL sel) {
    Class superCls = class_getSuperclass(cls);
    if (!superCls) return YES;
    IMP own   = class_getMethodImplementation(cls, sel);
    IMP parent = class_getMethodImplementation(superCls, sel);
    return (own != parent);
}

// 2. 安全 hook
static void purifySafeHook(Class cls, SEL sel, IMP replacement, IMP *orig) {
    if (purifyIsOverridden(cls, sel)) {
        // 覆写了 → 直接 MSHookMessageEx（= 微信优化策略）
        MSHookMessageEx(cls, sel, replacement, orig);
        return;
    }
    // 未覆写 → class_addMethod 在子类创建独立方法副本 → 再 hook
    Method parentMethod = class_getInstanceMethod(class_getSuperclass(cls), sel);
    IMP parentIMP = method_getImplementation(parentMethod);
    const char *types = method_getTypeEncoding(parentMethod);
    class_addMethod(cls, sel, parentIMP, types);
    MSHookMessageEx(cls, sel, replacement, orig);
    // _orig = 父类原始 IMP，与父类 hook 完全隔离
}
```

### 关键点

- `class_addMethod` 在子类方法表中创建**独立条目**，指向父类原始 IMP
- `MSHookMessageEx` 只修改这个本地副本
- 父类方法表完全不动
- `_orig` = 父类原始 IMP，不可能指向父类 hook

### 适用范围

| 类 | 策略 | 原因 |
|----|------|------|
| `ChatTimeCellView` | 直接 MSHookMessageEx | 上层类，无子类 hook 冲突 |
| `SystemMessageCellView` | **purifySafeHook** | TintHook 修改了 Base 层，需隔离 |
| `AppPatMessageCellView` | **purifySafeHook** | SysCell 的子类，需隔离父类 hook |
| `ChatTimeViewModel` | 直接 MSHookMessageEx | 上层类 |
| `SystemMessageViewModel` | **purifySafeHook** | 可能有 TintHook 等模块影响 |
| `AppPatMessageViewModel` | **purifySafeHook** | SysVM 的子类 |

## 失败经历 & 根因分析

| 尝试 | 做法 | 结果 | 根因 |
|------|------|------|------|
| 移除 setFrame | 只 setHidden:YES | 有空白占位 | setFrame 触发 setNeedsLayout，协同 shouldLayoutIfNeeded=NO |
| 移除 purifySafeHook | 全部直接 MSHookMessageEx | 布局错乱 + 交叉污染 | _orig 指向父类 hook，形成链：Pat hook→Sys hook→原始 |
| Sys-before-Pat + purifySafeHook(Pat) | 只保护子类 | Pat 正常，Sys 布局错乱 | SysCell 自身继承自 Base 层，被 TintHook 污染 |
| **最终方案** | Sys+Pat 全用 purifySafeHook | ✓ 正常工作 | 两边都通过 class_addMethod 隔离 |

## 模块交互

### TintHook

`TintHook.m` 用 `method_setImplementation` 直接修改 `BaseMessageCellView` 的 `updateStatus`/`layoutContentView`。这会污染 Base 层的方法表。

当 `SystemMessageCellView` 未覆写 `canBeReused` 等继承方法时，直接 `MSHookMessageEx` 会穿透到被污染的 Base 层。

**解决方案**: purifySafeHook 的 `class_addMethod` 在 SysCell 层创建独立副本，隔离 Base 层的污染。

### RevokeHandler

`RevokeHandler` 处理防撤回逻辑（自定义撤回提示文本），与 UIPurifyHook 的隐藏功能正交——两者不冲突。

- RevokeHandler 创建自定义撤回消息
- UIPurifyHook 控制撤回/拍一拍 Cell 的显示/隐藏

## 编译 & MRC 注意事项

- 项目已切换为 MRC（Manual Reference Counting）
- `MSHookMessageEx` 在 MRC 下无 trampoline 冲突
- NSUserDefaults 返回值需注意 retain/release（purifyReadConfig 返回 BOOL 无此问题）
- `CGSize` 是 struct 返回，走寄存器，无 ARC/MRC 影响

## 验证方法

1. 单独开启 `HideRevokeHint`：撤回消息消失，其他消息正常，布局不错乱
2. 单独开启 `HidePatHint`：拍一拍消息消失，撤回消息不受影响，布局不错乱
3. 同时开启两者：都消失，布局正常
4. 开启→发送消息→关闭→检查：被隐藏的消息不再出现（cell 被正确复用/丢弃）
