## 一、闪退信息摘要

### 1.1 异常类型

```
exception:   EXC_BAD_ACCESS (SIGSEGV)
subtype:     KERN_INVALID_ADDRESS at 0x0000000000000020
faultingThread: 0 (主线程)
```

### 1.2 关键寄存器

| 寄存器 | 值 | 含义 |
|--------|-----|------|
| `pc` | 0x1843A2304 | `objc_autoreleaseReturnValue + 76` |
| `far` | 0x20 | 无效地址（崩溃原因） |
| `esr` | 0x91C00006 | Data Abort, byte read Translation fault |

**结论**：代码尝试从地址 `0x20` 读取数据，这是一个**空指针解引用**（nil 对象的属性访问，属性偏移量为 32 字节）。

### 1.3 进程环境

设备加载了 **9 个 dylib 插件 + substrate 运行时**：

| # | dylib | 说明 |
|---|-------|------|
| 1 | `插件收纳.dylib` | 第三方插件 |
| 2 | `Mio_arm64-1-1.dylib` | **本插件** |
| 3 | `黄白助手 2.1.2.dylib` | 第三方插件 |
| 4 | `WCRefine 1.4.5.dylib` | 第三方插件 |
| 5 | `微信优化1.6.5.dylib` | 第三方插件 |
| 6 | `锤子助手2.4.1.dylib` | 第三方插件 |
| 7 | `MikotoHelper.dylib` | 第三方插件 |
| 8 | `微信助手 3.9-5.dylib` | 第三方插件 |
| 9 | `HBB.dylib` | 第三方插件 |
| - | `libsubstrate.dylib` | Hook 运行时 |

### 1.4 内核诊断

```
ktriageinfo:
  mach_vm_allocate_kernel failed within call to vm_map_enter
  mach_vm_allocate_kernel failed within call to vm_map_enter
  mach_vm_allocate_kernel failed within call to vm_map_enter
```

**含义**：在闪退发生前，系统内核已报告多次内核内存分配失败。这是**内存压力**的明确信号。

## 二、崩溃调用链分析

### 2.1 完整调用栈

```
frame 0: libobjc.A.dylib
         objc_autoreleaseReturnValue + 76
         ← 返回一个已经被释放或未初始化的对象

frame 1: 微信优化1.6.5.dylib + 0x3D19C (offset: 250268)
         ← 闪退的直接调用点，在此调用 objc_autoreleaseReturnValue 时崩溃

frame 2: UIKitCore
         -[UIView(CALayerDelegate) layoutSublayersOfLayer:] + 1528
         ← 视图布局阶段

frame 3: QuartzCore
         CA::Layer::layout_if_needed(CA::Transaction*) + 500

frame 4: UIKitCore
         -[UIView(Hierarchy) layoutBelowIfNeeded] + 296

frame 5+: 更多 UI 布局和微信业务代码
```

### 2.2 调用链解读

```
[微信业务代码触发 UI 更新]
    ↓
[UIView layoutBelowIfNeeded]  — 触发布局
    ↓
[CA::Layer::layout_if_needed] — CoreAnimation 布局
    ↓
[UIView layoutSublayersOfLayer:] — UIKit 布局子视图
    ↓
[微信优化1.6.5.dylib + 0x3D19C] — ★ 闪起点 ★
    ↓ 调用
[objc_autoreleaseReturnValue]   — ★ 崩溃点 ★
    尝试对地址 0x20 发送消息/读取数据 → SIGSEGV
```

### 2.3 崩溃机制

```
某对象指针 = nil (0x0)
    ↓
代码访问 [obj property] 或 obj->ivar
    ↓  property/ivar 偏移量为 32 字节 (0x20)
实际访问地址 = 0x0 + 0x20 = 0x20
    ↓
EXC_BAD_ACCESS (KERN_INVALID_ADDRESS)
```

**关键问题**：某对象为 nil，但代码未做判空检查，直接访问了该对象的属性/实例变量。

## 三、根因定位

### 3.1 直接原因

**微信优化1.6.5.dylib** 在 `offset 0x3D19C` 处的代码，对一个 nil 对象调用了 `objc_autoreleaseReturnValue`，导致访问地址 `0x20` 崩溃。

### 3.2 根本原因

结合 `ktriageinfo` 中的内核内存分配失败记录，判断根因是**内存压力过大导致的对象分配失败**：

```
内存压力增大
    ↓
插件数量过多（9个 dylib）+ WeChat 自身内存占用
    ↓
系统内核 vm_map_enter 分配失败
    ↓
微信优化1.6.5.dylib 中某对象分配返回 nil
    ↓
对 nil 对象访问属性 → offset 0x20 处读取 → SIGSEGV
```

### 3.3 触发场景

崩溃发生在 **UIKit 布局阶段**（`layoutSublayersOfLayer`），说明是在界面渲染/刷新时触发。可能触发场景：

| 场景 | 可能性 |
|------|--------|
| 进入聊天列表/会话界面 | 高 |
| 切换 Tab | 中 |
| 收到新消息后 UI 刷新 | 高 |
| 启动后首次渲染 | 中 |
| 后台回前台重新布局 | 中 |

### 3.4 与本插件的关系

**本插件（Mio_arm64-1-1.dylib）不是直接原因。** 原因：

1. 调用栈 frame 1 显示闪退在 **微信优化1.6.5.dylib**，不是 Mio
2. 闪退类型是内存压力下的 nil 指针解引用，属于插件冲突/环境问题
3. 当前 `TintHook.m` 中 Hook 代码为空（SKIPPED），没有活跃的 Hook 会影响运行时

## 四、修复方案

### 方案一：减少同时加载的插件数量（推荐）

**问题**：9 个 dylib 同时加载到微信进程中，显著增加内存压力。

**操作**：
1. 检查手机中已安装的插件列表，移除不需要的冗余插件
2. 保留核心插件（如本插件），禁用功能重叠的第三方插件
3. 特别是以下插件功能可能存在重叠：
   - `微信优化1.6.5.dylib` — 功能与本插件和 WCRefine 重叠
   - `WCRefine 1.4.5.dylib` — 圆角/美化功能与本插件重叠
   - `锤子助手2.4.1.dylib` — 综合功能可能与其他插件重叠

### 方案二：在本插件中兼容处理

如果无法减少插件数量，可以在本插件启动时检测微信优化 dylib 的加载，避免 Hook 冲突：

**检查点**：在 `Tweak.m` 或 `HookRegistry` 的初始化入口，检测是否存在已知冲突的插件。

```objc
// 检测微信优化是否已加载
BOOL hasWeChatOptimize = (objc_getClass("某个微信优化独有的类") != nil);

// 检测 WCRefine 是否已加载
BOOL hasWCRefine = (objc_getClass("某个WCRefine独有的类") != nil);

// 如果冲突插件已加载，跳过有冲突的 Hook 或使用兼容模式
```

具体需要分析微信优化和 WCRefine 中与本插件重叠的功能点。

### 方案三：延迟加载部分功能

将部分非核心 Hook 延迟到微信启动完成后再注册，避免启动时的内存峰值：

```objc
// 在 Tweak.m 中
__attribute__((constructor))
static void WeChatPluginInitialize() {
    // 核心功能立即注册
    [HookRegistry installEssentialHooks];
    
    // 非核心功能延迟注册（如名字颜色、UI 美化等）
    dispatch_after(dispatch_time(DISPATCH_TIME_NOW, 5 * NSEC_PER_SEC),
                   dispatch_get_main_queue(), ^{
        [HookRegistry installOptionalHooks];
    });
}
```

### 方案四：添加异常保护（防御性编程）

在本插件的所有 Hook 函数中添加 nil 检查，即使传入的对象为 nil 也不崩溃：

**当前所有 Hook 函数**（需要检查和修复的包括但不限于）：

| 文件 | 函数 | 检查点 |
|------|------|--------|
| `ProfileCardBgHook.m` | `applyProfileCardCorner` | cell 是否为 nil |
| `ProfileCardBgHook.m` | `cleanNativeBgImageView` | view 是否为 nil |
| `ListCornerRadiusHook.m` | `wp_applyBorderAndBg` | cell 是否为 nil |
| `ListCornerRadiusHook.m` | `applyCornerWithConfig` | 所有参数判空 |
| `所有使用 `objc_getClass` 的地方` | — | 检查返回的 Class 是否为 nil |
| `所有使用 `MSHookMessageEx` 的地方` | — | 检查 class 是否为 nil |

## 五、预防措施

### 5.1 内存监控

在插件中添加内存压力检测：

```objc
// 在关键操作前检查内存状态
#import <mach/mach.h>

BOOL isMemoryUnderPressure(void) {
    struct vm_statistics64 stats;
    mach_msg_type_number_t count = HOST_VM_INFO64_COUNT;
    kern_return_t ret = host_statistics64(mach_host_self(),
                                           HOST_VM_INFO64,
                                           (host_info64_t)&stats,
                                           &count);
    if (ret != KERN_SUCCESS) return NO;
    
    // 如果空闲内存低于阈值，返回 YES
    return (stats.free_count * vm_page_size) < 50 * 1024 * 1024; // 50MB 阈值
}
```

### 5.2 Hook 安全规范

所有 Hook 函数强制执行以下安全规范：

1. **每个 Hook 函数第一行做 nil 检查**
2. **`objc_getClass` 的返回值必须判空**
3. **`object_getIvar` 的返回值必须判空**
4. **`MSHookMessageEx` 调用前 class 不为 nil**
5. **所有 `@try/@catch` 中 catch 块不能为空，至少要输出日志便于排查**

### 5.3 启动加载优化

| 优化项 | 说明 |
|--------|------|
| 延迟非核心 Hook | 启动 5 秒后再注册非关键 Hook |
| 按需加载 | 用户进入对应设置页后再注册对应 Hook |
| 懒加载 | 使用 `dispatch_once` 确保只初始化一次 |
