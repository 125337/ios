# 列表圆角 + 卡片背景同时开启卡死 — 精确匹配微信优化改造方案（方式一）

## 概述

本方案旨在通过改造 MioPlugin 的代码，使其在处理列表圆角 + 卡片背景同时开启时的行为**精确匹配微信优化**，从根本上消除布局循环导致的看门狗超时（0x8BADF00D）。

基于对微信优化反编译代码（`wxyh1.6.5.dylib.c`）的深度分析，识别出 **3 个关键差异**，需对应改造。

---

## 一、根因回顾

### 1.1 崩溃事实

- **崩溃类型**：看门狗超时（`0x8BADF00D`），主线程卡死 5+ 秒
- **触发条件**：列表圆角（`listCornerRadiusEnabled`）+ 卡片背景（`cardBgEnabled`）同时开启，进入"我的"页面
- **直接原因**：`currentX != targetX` 使用 `==` 比较浮点数，永不收敛
- **深层原因**：即使修了浮点比较，Cell Hook 和 Button Hook 每轮 layoutSubviews 都多重修改 frame，放大震荡

### 1.2 微信优化为什么不会崩溃

微信优化通过以下 4 个机制避免了问题：

| 机制 | 微信优化 | MioPlugin |
|------|---------|-----------|
| **① margin 执行时机** | **仅在 bg 创建时执行 1 次** | **每次 layoutSubviews 都执行** |
| **② 浮点数处理** | 使用整数（`long`）运算 | 使用 `CGFloat` + `==` 比较 |
| **③ Button Hook 分离** | 2 个独立 MSHook（轻重分离） | 1 个 Hook 做所有事 |
| **④ Cell Hook 轻量** | 仅设默认 bgColor | 每次解析自定义 bgColor |

**本方案针对①、②进行改造**（③、④为优化项，非必须）。

## 三、改造 A：Cell Hook 浮点比较修复

### 3.1 当前代码

文件：`ListCornerRadiusHook.m` 第 214-231 行

```objc
// ★ margin 代码（只在 listCornerRadiusEnabled 时执行，进入此处说明已开启）★
CGFloat margin = config.listCellMargin;
if (margin > 0) {
    CGFloat currentX = cellView.frame.origin.x;
    UIView *superview = cellView.superview;
    CGFloat superX = superview ? superview.frame.origin.x : 0;
    CGFloat targetX = (margin > superX) ? margin - superX : 0;
    CGFloat containerW = superview ? superview.bounds.size.width
                                   : [UIScreen mainScreen].bounds.size.width;
    CGFloat targetW = containerW - 2.0 * margin;
    CGFloat currentW = cellView.frame.size.width;
    if (currentX != targetX || fabs(currentW - targetW) > 0.5) {  // ← BUG
        CGRect f = cellView.frame;
        f.origin.x = targetX;
        f.size.width = targetW;
        cellView.frame = f;
    }
}
```

### 3.2 Bug 分析

`currentX != targetX` 是 `CGFloat` 之间的 `==` 比较。由于浮点精度：
- UIKit 可能将 `9.0` 存储为 `8.999999`
- 每次比较 `8.999999 != 9.0` → `YES`
- Cell Hook 每次都想"修正" frame
- 配合 Button Hook 的 layout 触发 → 永不收敛

### 3.3 改造代码

```objc
// 第 225 行：替换比较条件
if (fabs(currentX - targetX) > 0.5 || fabs(currentW - targetW) > 0.5) {
```

### 3.4 微信优化参照

微信优化 Cell Hook（FUN_0000b4cc）使用整数读取配置：

```c
lVar9 = FUN_000c6960(uVar5, ..., &cf_CellHorizontalMargin);  // 返回 long
//...
dVar25 = (double)lVar9;  // 仅计算时转 double
```

整数不存在精度问题。

## 四、改造 B：Cell Hook 跳过资料卡 cell margin

### 4.1 原因

当列表圆角 + 卡片背景同时开启时：
- **Cell Hook** 调整 cell.frame（margin）  
- **Button Hook** 调整 button.frame（margin + height）
- 两者都在 layoutSubviews 中执行，互相触发

对于资料卡（MoreViewController）的 cell，其宽度应该由 Button Hook 统一管理。Cell Hook 不应再调整资料卡 cell 的 frame。

### 4.2 改造代码

在 `ListCornerRadiusHook.m` 第 212 行（`UIView *cellView = (UIView *)self;`）之后、第 214 行（margin 代码）之前插入：

```objc
UIView *cellView = (UIView *)self;

// ★★ 改造 B：资料卡 cell 的 margin 由 Button Hook 统一处理 ★★
if ([className isEqualToString:@"MoreViewController"]) {
    goto AFTER_MARGIN;
}

// ★ margin 代码 ★
```

同时确保 margin 代码块**之后**（第 231 行处）有 `AFTER_MARGIN:` 标签。当前代码第 231 行是关闭 `if (margin > 0)` 的 `}`，可以在其后添加：

```objc
    } // ← 第 231 行，关闭 if (margin > 0)
}
AFTER_MARGIN:  // ★ 新增标签 ★
```

### 4.3 微信优化参照

微信优化的 Cell Hook（FUN_0000b4cc）没有显式的"跳过资料卡"逻辑，但它的 Button Hook margin 在创建分支内，不涉及 Cell↔Button 双重修改。MioPlugin 需要这个跳过逻辑来弥补 margin 每轮都执行的差异。

## 五、改造 C：Button Hook margin 移到创建分支内

### 5.1 这是最关键的改造

当前 MioPlugin 的 margin 调整**每轮 layoutSubviews 都执行**：

```objc
// ProfileCardBgHook.m L541-554（当前在 bg 生命周期外面）

    !(config.cardBgFillMode == 3 && config.cardBgEnabled)) {
    CGFloat margin = config.listCellMargin;
    if (margin > 0) {
        CGRect bf = button.frame;
        bf.origin.x += margin;
        bf.size.width -= margin * 2;
        button.frame = bf;  // ← 每轮都执行
    }
}
```

微信优化只在 **bg 创建时** 执行 1 次：

```c
// 微信优化 FUN_00007b4c 创建分支（LAB_000082c8）
// ...

    margin = CellHorizontalMargin;

}

// [button addSubview:bg];
// dispatch_async 加载图片...
// ← 创建完成后，后续 layoutSubviews 不再调整 margin
```

#### 步骤 1：在 bg 创建分支内添加 margin 调整

将帧计算修改为根据 margin 调整 bg 的 frame，同时保留 offsetX/offsetY：

分支 A 中更新 bg frame 时也需要考虑 margin，匹配微信优化"每次更新 frame（不含 margin 调整）"的行为：

## 八、风险与注意事项

### 8.1 已知风险

| 风险 | 说明 | 缓解措施 |
|------|------|---------|
| **bg 创建后 button 宽度变化** | 如果 iOS 系统布局后续调整了 button 的宽度，bg 宽度不会自动跟随调整 | 分支 A 中 bgImgView.frame 使用 button.bounds.size.width 计算，会自动跟随 |
| **margin 只在创建时生效** | 用户退出再进入"我的"页面时，bg 会被重新创建，margin 重新应用 | 这是正常行为，与微信优化一致 |
| **同时开启 HideCard** | HideCard 分支中 button.subviews 被隐藏，bg 通过 tag 豁免 | 已验证，bg 保留可见 |

### 8.2 耦合性分析

| 改造 | 影响其他功能 | 说明 |
|------|------------|------|
| 改造 A：fabs 比较 | ❌ 不影响 | 所有页面公用，fabs 更精确 |
| 改造 B：跳过资料卡 cell margin | ⚠️ 仅影响资料卡 | 非资料卡页面不受影响 |
| 改造 C：margin 移到创建分支 | ⚠️ 仅影响资料卡 bg 创建 | bg 创建后不再调整 button 宽度 |

### 8.3 回滚方案

按改造顺序反向回滚：
1. 恢复 `ProfileCardBgHook.m` L541-554 的独立 margin 块
2. 恢复 `ListCornerRadiusHook.m` L225 的 `==` 比较
3. 删除 `ListCornerRadiusHook.m` 的跳过逻辑和 `AFTER_MARGIN` 标签
