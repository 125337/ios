## 一、从日志直接提取的微信实际行为

### 1.1 整体诊断结论

从 `MioPlugin(7).log` 提取所有关键信息：

| 诊断项 | 日志内容 | 结论 |
|-------|---------|------|
| Hook 安装 | `MMThemeManager: EXISTS` / `CLocalInfo: EXISTS` 方法均找到 | ✅ Hook 安装成功 |
| CLocalInfo | `m_uiGlobalFontLevel -> 1` (大字模式) 出现 100+ 次 | ✅ 大字模式已激活 |
| 配置值 | `globalOn=1 globalSize=14 chatOn=1 chatSize=14` | ✅ 配置正确读取 |
| **MMTM 匹配** | **`⚡ HIT` 日志出现 0 次** | ❌ **Hook 从未拦截到任何调用** |
| 原方法返回值 | 全部为 `__NSArrayM` (NSMutableArray) | ❌ 返回值是数组，不是字符串/数字 |

### 1.2 微信实际调用的属性名和规则集

通过日志中的 `[MMTM] property=xxx ruleSet=yyy` 记录，统计如下：

| property | ruleSet | origType | origValue | 出现次数 | 含义 |
|----------|---------|----------|-----------|---------|------|
| `titleview_fontsize` | `#navigation_bar` | `__NSArrayM` | `@[17]` | ~50+ | 导航栏标题字号 |

| `text_font` | `#widget_tipsbar_base` | `__NSArrayM` | `@[14, @"dynamic"]` | 1 | Tipsbar 文本字号 |
| `footer_nomore_msg_font` | `#brand_timeline_view` | `__NSArrayM` | `@[@"12.0", @"dynamic"]` | 1 | 朋友圈底部无更多消息字号 |

### 1.3 返回值结构（关键发现）

返回值类型统一为 `__NSArrayM`（NSMutableArray），数组结构分三种：

```
类型A：@[ NSNumber ]                     → 如 @[17]     （titleview_fontsize, common_font_small_size）
类型B：@[ NSNumber, NSString ]           → 如 @[17, @"dynamic"]  （tool_view_fontSize, text_font）
类型C：@[ NSString, NSString ]           → 如 @[@"12.0", @"dynamic"]  （footer_nomore_msg_font）
```

**第一个元素始终是字号大小**，类型可能是 NSNumber 或 NSString。
**第二个元素（有则）是修饰符**，如 `@"dynamic"`。

### 1.4 规则集命名规律

所有规则集以 `#` 前缀开头，不使用 `_font_set` 后缀：

```
#navigation_bar        → 导航栏
#common_default        → 通用默认
#input_tool_view_tool  → 输入工具栏
#widget_tipsbar_base   → Tipsbar 组件
#brand_timeline_view   → 品牌朋友圈
```

## 二、当前实现与微信实际行为的对比

### 2.1 属性/规则集匹配差异（根因）

```objc
// 当前代码（从未命中）
if ([ruleSet hasSuffix:@"_font_set"]) {          // 检查 _font_set
    if ([property isEqualToString:@"allLevel"]   // 检查 allLevel
     || [property isEqualToString:@"webLevel"])  // 检查 webLevel
}

// 微信实际调用
property=titleview_fontsize    ruleSet=#navigation_bar
property=common_font_small_size ruleSet=#common_default
property=tool_view_fontSize     ruleSet=#input_tool_view_tool
```

**对比结果**：
- `ruleSet` 匹配：`hasSuffix:@"_font_set"` vs `#navigation_bar`、`#common_default` → **不命中**
- `property` 匹配：`allLevel` vs `titleview_fontsize`、`common_font_small_size` → **不命中**
- **结论：当前所有条件均不满足，Hook 永远走 fallback 返回原方法值**

### 2.2 返回值类型差异

```objc
// 当前代码
return [NSString stringWithFormat:@"%.0f", fontSize];   // 返回 NSString

// 微信实际
__NSArrayM @[17]  → 需要返回 NSArray
__NSArrayM @[17, @"dynamic"]  → 需要返回 NSArray
```

即使属性名匹配上，返回 NSString 也会被微信忽略（微信期望 NSArray）。

### 2.3 大字模式 vs 具体布局修改

从日志看，`m_uiGlobalFontLevel -> 1` 已被正确触发，但大字模式可能只是让微信使用预设的大字号配置（如 17pt），而不直接接受用户自定义的 14pt。

大字模式激活后，微信自身的字体表：
```
titleview_fontsize:     17 (大字模式)
common_font_small_size: 12 (大字模式)
```

用户希望的值 14pt 介于两者之间，但因为我们的 Hook 从未拦截到调用，微信继续使用原厂的 17/12 值。

## 三、锤子助手真正的工作原理（日志反推）

由于锤子助手在**同一个微信版本**有效，它必定做了和日志中实际调用相匹配的操作。

### 3.1 锤子助手的真正做法（推断）

锤子助手 FUN_00753950 的**真实**逻辑不是匹配具体属性名，而是：

```objc
- (id)hook_getValueOfProperty:(NSString *)property inRuleSet:(NSString *)ruleSet {
    // 1. 先调原方法（获取数组）
    id original = [self orig_getValueOfProperty:property inRuleSet:ruleSet];
    
    // 2. 检查是否为字体相关（用 containsString 更宽松的方式）
    if ([property containsString:@"font"] || [ruleSet containsString:@"font"]) {
        
        // 3. 取出 CSS 配置
        NSString *css = [WeChatTweakSettings changedCSSStr];
        
        // 4. 如果 original 是数组，修改第一个元素为 CSS 指定的值
        if ([original isKindOfClass:[NSArray class]] && css.length > 0) {
            NSMutableArray *modified = [original mutableCopy];
            CGFloat newSize = [self parseFontSizeFromCSS:css];
            // 保持原元素类型（NSNumber 保持 NSNumber，NSString 保持 NSString）
            if ([modified[0] isKindOfClass:[NSNumber class]]) {
                modified[0] = @((NSInteger)newSize);
            } else if ([modified[0] isKindOfClass:[NSString class]]) {
                modified[0] = [NSString stringWithFormat:@"%.0f", newSize];
            }
            return modified;
        }
    }
    
    return original;
}
```

关键特征：
1. **不匹配具体属性名**，而是用 `containsString:@"font"` 等宽松方式
2. **保留数组结构**，只修改第一个元素（字号）
3. **保留元素类型**，NSNumber → NSNumber，NSString → NSString
4. CSS 中存储的是目标字号值

### 3.2 锤子助手 vs 微信实际调用

| 环节 | 锤子助手做法 | 微信实际调用 | 匹配？ |
|------|------------|------------|-------|
| 属性匹配 | 宽松匹配（可能 check contains `font`） | `titleview_fontsize` | ✅ |
| 规则集匹配 | 宽松匹配 | `#navigation_bar` | ✅ |
| 返回值 | 修改 NSArray[0] 后返回 | `__NSArrayM` 数组 | ✅ |
| 大字模式 | `m_uiGlobalFontLevel=1` | 被多次调用 | ✅ |

## 四、正确的实现方案

### 4.1 核心思路

放弃具体属性名匹配，改为：

1. **检查返回值是否为数组**（所有 MMTM 调用返回数组）
2. **检查数组第一个元素是否为数值类型**（避免误改非字号属性）
3. **保留数组结构，只修改第一个元素**（字号）
4. **保留元素类型**（NSNumber 还是 NSString）

### 4.2 Hook 核心逻辑

```objc
static id hook_getValueOfProperty_inRuleSet(id self, SEL _cmd,
                                             NSString *property,
                                             NSString *ruleSet) {
    // 先调原方法获取原始值
    id originalResult = orig_getValueOfProperty_inRuleSet(self, _cmd, property, ruleSet);
    
    FontLayoutConfig *config = [FontLayoutConfig shared];
    BOOL globalOn = config.globalLayoutEnabled;
    BOOL chatOn   = config.chatLayoutEnabled;
    
    if (!globalOn && !chatOn) return originalResult;
    
    // 确定目标字号：全局布局用 globalFontSize，对话布局用 chatFontSize
    // 注意：这里简化了全局vs对话的区分逻辑，需要根据实际需求确定
    CGFloat targetSize = globalOn ? config.globalFontSize : config.chatFontSize;
    
    // 范围验证
    if (targetSize < 10.0f || targetSize > 16.0f) return originalResult;
    
    // 仅当返回值为数组时才修改（微信所有字体属性都返回 NSArray）
    if ([originalResult isKindOfClass:[NSArray class]]) {
        NSMutableArray *modified = [originalResult mutableCopy];
        if (modified.count == 0) return originalResult;
        
        id firstElement = modified[0];
        
        // 根据第一个元素的类型创建同类型的新值
        if ([firstElement isKindOfClass:[NSNumber class]]) {
            modified[0] = @((NSInteger)targetSize);
            return modified;
        } else if ([firstElement isKindOfClass:[NSString class]]) {
            modified[0] = [NSString stringWithFormat:@"%.0f", targetSize];
            return modified;
        }
    }
    
    return originalResult;
}
```

### 4.3 全局 vs 对话布局的区分策略

从日志看，微信没有单独的"对话布局"规则集，所有调用都是全局的。要实现对话布局差异：
- **方案A**：全局布局修改所有 font 属性，对话布局仅修改 `#common_default` 中的属性
- **方案B**：全局布局作为总开关，对话布局在总开关基础上做精细调整

需要根据产品需求确定交互逻辑。

### 4.4 规则集白名单（可选，防止误改非字号属性）

```objc
// 只修改已知的字体相关规则集（白名单方式）
static NSSet *s_fontRuleSets;
static dispatch_once_t onceToken;
dispatch_once(&onceToken, ^{
    s_fontRuleSets = [NSSet setWithObjects:
        @"#navigation_bar",
        @"#common_default",
        @"#input_tool_view_tool",
        @"#widget_tipsbar_base",
        @"#brand_timeline_view",
        nil];
});

if ([s_fontRuleSets containsObject:ruleSet]) {
    // 修改数组中的字号
}
```

## 五、从日志中确认的完整调用图谱

```
启动后首次加载:
  ├─ [CLocalInfo m_uiGlobalFontLevel]  → 1 (大字模式)
  ├─ [MMTM titleview_fontsize → #navigation_bar] → @[17]
  ├─ [MMTM common_font_small_size → #common_default] → @[12]
  ├─ [MMTM tool_view_fontSize → #input_tool_view_tool] → @[17, "dynamic"]
  ├─ [MMTM text_font → #widget_tipsbar_base] → @[14, "dynamic"]
  └─ [MMTM footer_nomore_msg_font → #brand_timeline_view] → @["12.0", "dynamic"]

每次导航栏显示:
  └─ [MMTM titleview_fontsize → #navigation_bar]  (反复调用，频率高)

每次列表/文本渲染:
  └─ [MMTM common_font_small_size → #common_default]  (反复调用，频率高)
```

注意：`[CLocalInfo m_uiGlobalFontLevel]` 的调用次数远多于 `[MMTM]`，说明微信内部频繁检查大字模式状态，但只有在需要渲染 UI 元素时才会调用 `MMThemeManager` 获取具体值。

## 七、总结

### 根本原因

我们的 Hook 函数中，属性匹配条件（`allLevel`/`webLevel`/`chatLevel` + `_font_set`）**与微信实际调用完全不匹配**，导致：
- `isFontRuleSet(ruleSet)` 对 `#navigation_bar` → **NO**
- `[property isEqualToString:@"allLevel"]` 对 `titleview_fontsize` → **NO**
- **所有条件都不满足，Hook 永远返回原方法值，我们的设置值 14 从未被使用**

### 需要做的修改

1. 放弃具体属性名匹配，改为宽松匹配（如检测返回值是否为数组且有字号元素）
2. 保留 NSArray 结构，只修改第一个元素
3. 保留元素类型（NSNumber 还是 NSString）
4. `CLocalInfo.m_uiGlobalFontLevel` 保持现有逻辑

### 日志中发现的额外问题（非关键）

`[UD Direct] globalOn=0 globalSize=0 chatOn=0 chatSize=0` — 用 `NSUserDefaults standardUserDefaults` 直接读原始 key 返回全 0，说明 ConfigManager 的 key 拼接机制与直接读取使用的 key 不同。但这不影响功能，因为 ConfigManager 内部读写路径是一致的。
