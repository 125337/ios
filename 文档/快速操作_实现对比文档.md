### 2.3 `getSessionInfo()` — 获取会话信息 ⭐差异较大

**文档描述**（伪代码级别）:
```objc
id sessionInfo = /* 从 self/tableView 获取对应 indexPath 的会话 */;
```

文档只给了方向性描述，实际实现非常完整。

**实际实现**（[QuickActionsHook.m:L12-L25](file:///www/wwwroot/ios/MioPlugin/Modules/QuickActions/QuickActionsHook.m#L12-L25)）:
```objc
static id getSessionInfo(id self, NSIndexPath *indexPath) {
    if ([self respondsToSelector:@selector(getSessionInfoAtIndexPath:)]) {
        return ((id (*)(id, SEL, id))objc_msgSend)(self, @selector(getSessionInfoAtIndexPath:), indexPath);
    }
    SEL logicSel = NSSelectorFromString(@"logicGetSessionAtIndexPath:");
    if ([self respondsToSelector:logicSel]) {
        return ((id (*)(id, SEL, id))objc_msgSend)(self, logicSel, indexPath);
    }
    id sessionMgr = [self valueForKey:@"m_sessionMgr"];
    if (sessionMgr && [sessionMgr respondsToSelector:@selector(getSessionInfoAtIndexPath:)]) {
        return ((id (*)(id, SEL, id))objc_msgSend)(sessionMgr, @selector(getSessionInfoAtIndexPath:), indexPath);
    }
    return nil;
}
```

**关键差异**:
1. 实际实现封装成独立函数，文档是内联伪代码
2. 实际实现有 **三层降级策略**：
   - 第1层: `[self getSessionInfoAtIndexPath:indexPath]` — 最直接
   - 第2层: `[self logicGetSessionAtIndexPath:indexPath]` — 反编译中发现的备选方法
   - 第3层: `[self valueForKey:@"m_sessionMgr"]` → `getSessionInfoAtIndexPath:` — 通过 ivar 间接获取

> 实际实现的降级策略比文档考虑的更加健壮，覆盖了反编译代码中发现的全部三种路径。

### 2.9 `replaced_trailingSwipeActionsConfig()` — Hook 核心 ⭐有多处差异

#### 2.9.1 原始方法调用保护

| 文档 | 实际 |
|------|------|
| 直接调用 `orig_trailingSwipeActionsConfig(self, _cmd, ...)` | **先判空**: `if (orig_trailingSwipeActionsConfig)` 再调用 |

```objc
// 文档 — 直接调用
id origConfig = ((id (*)(id, SEL, id, id))orig_trailingSwipeActionsConfig)(self, _cmd, tableView, indexPath);

// 实际 — 先判空再调用（更安全）
id origConfig = nil;
if (orig_trailingSwipeActionsConfig) {
    origConfig = ((id (*)(id, SEL, id, id))orig_trailingSwipeActionsConfig)(self, _cmd, tableView, indexPath);
}
```

> **评价**: 实际实现更安全。如果 `NewMainFrameViewController` 不实现 `trailingSwipeActionsConfiguration` 方法，`orig_trailingSwipeActionsConfig` 为 NULL，直接调用会崩溃。

#### 2.9.2 sessionInfo 获取失败日志

| 文档 | 实际 |
|------|------|
| 无日志 | `WPLog(@"QuickActions", @"[DEBUG] no sessionInfo for indexPath %@", indexPath);` |

> **评价**: 实际实现加了调试日志，方便排查。

#### 2.9.3 状态查询位置

| 文档 | 实际 |
|------|------|
| 在构建按钮之前统一查询 `isTop` 和 `isMuted` | 在主函数中查询一次，但 `handleMute()` 和 `handlePin()` 内部又**各自再次查询** |

```objc
// 主函数中查询 (L182-L192)
BOOL isTop = ...;  // 用于设置按钮标题
BOOL isMuted = ...; // 用于设置按钮标题

// handleMute 内又查一次 (L73-L77)
BOOL isMuted = ...; // 重复查询

// handlePin 内又查一次 (L127-L131)
BOOL isTop = ...; // 重复查询
```

> **评价**: 这是**冗余查询**，但不是 bug。按钮标题需要状态来决定显示"免打扰"还是"取消免打扰"，而 handler 内部再次查询是因为 handler 是独立函数不知道上层的状态。可以优化为传递状态参数，避免重复调用 `objc_msgSend`。

#### 2.9.4 userName 获取方式

| 文档 | 实际 |
|------|------|
| 伪代码 `/* 从会话获取 */` | 使用 `NSSelectorFromString(@"m_nsUserName")` + respondsToSelector 检查 |

实际实现更严谨，有 `respondsToSelector` 检查和空值判断。

#### 2.9.5 备注 completionHandler 调用时机 ⭐差异

| 文档 | 实际 |
|------|------|
| 在 handler block 最后调用 `completion(YES)` | **先调** `completionHandler(YES)`，再调 `handleRemark(contact)` |

```objc
// 文档
handler:^(...) {
    handleRemark(contact);  // 先处理
    completion(YES);        // 后完成
}

// 实际 (L205-L208)
handler:^(...) {
    completionHandler(YES); // 先完成动画
    handleRemark(contact);  // 后弹出 VC
}
```

> **评价**: 实际实现**更合理**。`handleRemark` 会 present 一个 ViewController，这个过程需要时间。如果等 present 完成再调 `completionHandler`，滑动动画会卡住很久。先让动画完成再弹 VC，用户体验更好。

#### 2.9.6 actions 数组合并

| 文档 | 实际 |
|------|------|
| `[ourActions arrayByAddingObjectsFromArray:origActions]` (不可变) | `NSMutableArray` → `addObjectsFromArray:` (可变) |

实际实现多了一步先创建 `NSMutableArray`，然后再合并。结果等价但实际代码更显式。

#### 2.9.7 origConfig actions 获取

| 文档 | 实际 |
|------|------|
| 伪代码 `/* origConfig.actions */` | 使用 `NSSelectorFromString(@"actions")` + `respondsToSelector` + 判空 |

实际实现使用 `objc_msgSend` 方式获取 `actions` 属性，而不是直接点语法，更符合无头文件环境下的调用规范。

### 2.10 `install()` 方法 — Hook 安装

#### 2.10.1 调试代码

| 文档 | 实际 |
|------|------|
| 调试代码作为"建议添加"放在正文步骤中 | **直接内置**在 install 中，每次启动都执行 |

**实际实现额外添加了**:
- 打印 `NewMainFrameViewController` 的所有方法列表（筛选 swipe/trailing/SessionInfo/getSession）
- 打印 `NewMainFrameViewController` 的所有 ivar 列表（筛选 session/Session）
- 如果类不实现 `trailingSwipeActionsConfiguration`，打印 **ERR 级别**日志

> **评价**: 实际实现将调试代码内置在 install 中，意味着每次插件加载时都会打印方法列表和 ivar 列表。这在生产环境中可能产生大量日志，但方便排查。建议后续移除或加 `#if DEBUG` 包裹。

#### 2.10.2 降级类处理

| 文档 | 实际 |
|------|------|
| `if (!targetClass)` 判断是否有值 | 同样的降级逻辑，但实际实现中 `if (!targetClass)` 的判断在**第一个 if 块之后**，不是 else-if |

```objc
// 文档 — 用 else 逻辑
if (targetClass) { ... }
if (!targetClass) { ... }  // 独立 if

// 实际 — 同样的独立 if 结构 (L275-L286)
if (!targetClass) {
    targetClass = objc_getClass("MMMainFrameViewController");
    ...
}
```

由于 `targetClass` 在第一个 if 块中不会被设为 nil，所以第二个 if 条件永远为 false（因为 `targetClass` 已经在上一行被赋值为 `NewMainFrameViewController`）。但 `objc_getClass` 可能返回 nil，此时第二个 if 将尝试 `MMMainFrameViewController`。

**这实际上是文档和实现共有的一个 bug**: 第一个 if 块中 `targetClass` 赋值了，但不等于 nil 时，第二个 `if (!targetClass)` 条件为 false，`MMMainFrameViewController` 降级永远不会执行。应该是：

```objc
if (targetClass) {
    // 检查是否响应 selector
    if ([targetClass instancesRespondToSelector:targetSel]) {
        // hook
    } else {
        targetClass = nil; // 重置，让降级逻辑生效
    }
}
if (!targetClass) {
    // 尝试降级类
}
```

> **实际影响**: 如果 `NewMainFrameViewController` 存在但不实现 `trailingSwipeActionsConfiguration`，降级到 `MMMainFrameViewController` 的逻辑不会生效。不过这在当前环境下不是问题，因为 `NewMainFrameViewController` 如果存在就应该实现了该方法。

## 三、整体差异总结

| 序号 | 差异项 | 文档 | 实际实现 | 评价 |
|------|--------|------|----------|------|
| 1 | `getSessionInfo` 降级策略 | 伪代码级别 | 3层降级（getSessionInfoAtIndexPath / logicGetSessionAtIndexPath / m_sessionMgr） | ⭐ 实际更健壮 |
| 2 | 原方法调用判空 | 直接调用 | 先判 NULL 再调用 | ⭐ 实际更安全 |
| 3 | 备注 completionHandler 顺序 | 先处理再完成 | 先完成再处理 | ⭐ 实际体验更好 |
| 4 | 状态重复查询 | 仅在主函数查询 | 主函数 + handler 内各查一次 | ⚠️ 性能微冗余 |
| 5 | 调试日志内置 | 建议添加 | 直接内置在 install 中 | ⚠️ 生产环境日志过多 |
| 6 | ContactInfoViewController 获取 | `objc_getClass` | `objc_getClass` + `NSClassFromString` 双保险 | ✅ 实际更严谨 |
| 7 | actions 属性获取 | 伪代码 | `NSSelectorFromString` + `respondsToSelector` | ✅ 实际更规范 |
| 8 | 降级类 else 分支 | 独立 if 判断 | 独立 if 判断 | ⚠️ 两者都有逻辑缺陷 |

## 四、文档未覆盖但实际实现的亮点

1. **`getSessionInfo` 三层降级**: 文档只提到了方向，实际实现把三种路径都写出来了，覆盖了反编译代码中的所有可能
2. **`NSSelectorFromString` 保护**: 对于不确定是否存在的方法，全部用 `NSSelectorFromString` + `respondsToSelector` 包裹
3. **`objc_getClass` + `NSClassFromString` 双保险**: 获取 ContactInfoViewController 时两种方式都试
4. **空值防御链**: `window`、`sessionInfo`、`userName`、`contact`、`origConfig` 每个环节都有判空
5. **ERR 级别日志**: 当 Hook 不成功时打印错误日志，方便定位问题
