# 撤回/拍一拍隐藏导致布局错乱 — 根因分析与修复方案

## 问题现象

开启「隐藏撤回消息提示」或「隐藏拍一拍提示」后，聊天列表出现 **布局错乱、消息严重偏移**。

---

## 一、逐行对比：当前实现 vs 微信优化反编译

### 1.1 对比矩阵总览

| Hook 方法 | 微信优化反编译（123456.c） | 当前实现（UIPurifyHook.m） | 差异 |
|---|---|---|---|
| `initWithViewModel:` | `setHidden:YES` + `frame` + `setFrame:frame` | `setHidden:YES` + `alpha = 0` | **缺 `setFrame:`** |
| `layoutInternal` | 启用时跳过原方法 | 启用时跳过原方法 | 一致 |
| `canBeReused` | 返回 `YES` | 返回 `YES` | 一致 |
| `shouldLayoutIfNeeded` | 返回 `NO` | 返回 `NO` | 一致 |
| `measure:` | **不调用原方法**（返回 CGSizeZero） | 返回 `CGSizeMake(width, CGFLOAT_MIN)` | **根因** |

### 1.2 initWithViewModel: 对比

**微信优化 — `FUN_00025c48`（L23079-23105）：**

```c

    // 读取 NSUserDefaults
    if (enabled) {
        auVar5 = _objc_retain(lVar2);
        uVar3 = auVar5._0_8_;
        FUN_000cba80(uVar3, auVar5._8_8_, 1);    // ← [result setHidden:YES]
        FUN_000c58c0(uVar3);                       // ← [result frame]
        FUN_000cb900(uVar3);                       // ← [result setFrame:result.frame]

```

**我们的代码 — `hook_SysCell_initWithViewModel`：**

```objc
id result = ((id (*)(id, SEL, id))_orig...)(self, _cmd, viewModel);

if (purifyReadConfig(@"HideRevokeHint")) {
```

**差异 #1：** 微信优化在 `setHidden:YES` 之后**额外调用了 `setFrame:self.frame`**。虽然设置的值完全相同，但这个调用会触发 UIKit 内部布局失效标记（`setNeedsLayout`），让 TableView 意识到该 Cell 的布局已变化。

### 1.3 measure: 对比 — 这是根因

**微信优化 — `FUN_00025eb4`（L23172-23188）：**

```c

```

Ghidra 伪代码解读：

- `auVar2._8_8_ = 0` — 返回值的 height 字段被**显式置为 0**
- `auVar2._0_8_ = param_1` — width 字段为寄存器残留值，但由于 height=0，TableView 仍按零高度处理
- **关键：** 启用时不调用原始 `measure:`，直接构造返回值 — height 明确为 **0**

**我们的代码：**

```objc
static CGSize hook_SysVM_measure(id self, SEL _cmd, CGSize size) {
    if (purifyReadConfig(@"HideRevokeHint"))
        return CGSizeMake(size.width, CGFLOAT_MIN);  // ← 根因
    return ((CGSize (*)(id, SEL, CGSize))_orig_SysVM_measure)(self, _cmd, size);
}
```

**差异 #2（根因）：** `CGFLOAT_MIN` ≠ `0`

| 值 | 实际大小 | TableView 行为 |
|---|---|---|
| `CGSizeZero` | `{0.0, 0.0}` | 分配零空间，Cell 完全不影响布局 |
| `CGFLOAT_MIN` | `{宽度, ~1.18e-38}` | 分配 **正的非零微量高度**，引发精度问题 |

## 二、为什么 `CGFLOAT_MIN` 会导致布局错乱

### 2.1 UITableView 的高度计算链路

```
TableView 需要显示 Cell
    │
    ├─ tableView:heightForRowAtIndexPath:
    │       │
    │       ▼
    │   调用 ViewModel.measure: → 返回 CGSize
    │       │
    │       ▼
    │   height = measure返回值.height   ← 【这里拿到 CGFLOAT_MIN】
    │       │
    │       ▼
    │   TableView 分配高度 = 1.175e-38 px
    │       │
    │       ▼
    │   CGFloat 累加计算时出现精度损失
    │   后续 Cell 的 y 坐标 = 前面所有 Cell 高度之和
    │   含 CGFLOAT_MIN 的累积 → 误差逐行放大
    │       │
    │       ▼
    │   ！！！布局偏移 ！！！
```

### 2.2 为什么微信优化的 `CGSizeZero` 没问题

```
TableView 分配高度 = 0.0
    │
    ▼
CGFloat 累加计算：0 + 0 = 0（无精度损失）
    │
    ▼
后续 Cell 的 y 坐标完全不受影响
    │
    ▼
布局正确 ✓
```

### 2.3 `CGFLOAT_MIN` 的精确值

```c
#define CGFLOAT_MIN FLT_MIN
#define FLT_MIN     1.175494351e-38F   // 约 0.00000000000000000000000000000000000001175

// 对比：
CGFLOAT_MIN  = 1.175494351e-38   // 非零！是正数！
0.0          = 0.000000000000000   // 真正的零
```

虽然 `CGFLOAT_MIN` 极其微小，但在 CGFloat 浮点运算中，非零值参与累加会产生舍入误差。随着聊天列表不断滚动和 Cell 复用，这些微小误差会累积成肉眼可见的偏移。

## 三、第二原因：`initWithViewModel:` 缺 `setFrame:` 调用

### 3.1 UIKit 内部发生了什么

```
Cell 创建流程：
1. TableView 调用 dequeueReusableCell → 获取或创建 Cell
2. Cell.initWithViewModel: 被调用
     ├─ 原始代码设置 frame = {某些值, 某些值, w, h}   ← 微信原生布局
     ├─ 我们的 Hook: setHidden:YES + alpha = 0
     └─ 此时 frame 仍然是微信原生的布局值             ← 问题！
3. TableView 根据 measure: 结果重新布局 Cell
     ├─ measure: 返回 {w, CGFLOAT_MIN}
     └─ TableView 用 CGFLOAT_MIN 高度重新设置 frame
4. 但 Cell 的 subviews 仍然按原始 frame 布局
     └─ 内外 frame 不一致 → 子视图错位
```

### 3.2 微信优化如何避免

```
Cell 创建流程（微信优化版）：
1. TableView 调用 dequeueReusableCell
2. Cell.initWithViewModel: 被调用
     ├─ 原始代码设置 frame
     ├─ setHidden:YES                          ← 隐藏
     └─ setFrame:self.frame                     ← 触发 setNeedsLayout！
3. TableView 收到 "Cell 需要重新布局" 的信号
4. TableView 根据 measure: 结果（CGSizeZero）重新布局
     └─ 所有子视图也使用零高度布局 → 一致 ✓
```

`setFrame:` 内部会调用 `setNeedsLayout`，标记该视图需要重新布局。这通知 UIKit 的布局引擎该 Cell 的状态已改变，需要在下一个布局周期中重新计算所有子视图位置。

---

## 四、修复方案

### 修复项 1：`measure:` 返回 `CGSizeZero`（主要修复）

**文件：** `UIPurifyHook.m`

**当前（问题代码）：**

```objc
// hook_SysVM_measure — L105-109
if (purifyReadConfig(@"HideRevokeHint"))
    return CGSizeMake(size.width, CGFLOAT_MIN);   // ❌

// hook_PatVM_measure — L155-159
if (purifyReadConfig(@"HidePatHint"))
    return CGSizeMake(size.width, CGFLOAT_MIN);   // ❌
```

**修复后：**

```objc
// hook_SysVM_measure
if (purifyReadConfig(@"HideRevokeHint"))
    return CGSizeZero;                             // ✓ 完全匹配微信优化

// hook_PatVM_measure
if (purifyReadConfig(@"HidePatHint"))
    return CGSizeZero;                             // ✓ 完全匹配微信优化
```

### 修复项 2：`initWithViewModel:` 补充 `setFrame:` 调用（辅助修复）

**当前（问题代码）：**

```objc
// hook_SysCell_initWithViewModel — L35-43
if (purifyReadConfig(@"HideRevokeHint")) {
    UIView *v = (UIView *)result;
    [v setHidden:YES];
    v.alpha = 0;
    // ❌ 缺 setFrame:
}

// hook_PatCell_initWithViewModel — L127-133
if (purifyReadConfig(@"HidePatHint")) {
    UIView *v = (UIView *)result;
    [v setHidden:YES];
    v.alpha = 0;
    // ❌ 缺 setFrame:
}
```

**修复后（匹配微信优化 FUN_00025c48 + FUN_00025f64）：**

```objc
// hook_SysCell_initWithViewModel
if (purifyReadConfig(@"HideRevokeHint")) {
    UIView *v = (UIView *)result;
    [v setHidden:YES];
    v.frame = v.frame;               // ✓ 触发 setNeedsLayout，匹配微信优化
}

// hook_PatCell_initWithViewModel
if (purifyReadConfig(@"HidePatHint")) {
    UIView *v = (UIView *)result;
    [v setHidden:YES];
    v.frame = v.frame;               // ✓ 触发 setNeedsLayout，匹配微信优化
}
```

> **说明：** `v.frame = v.frame` 看起来是"无操作"，但实际上 `UIView.setFrame:` 内部会检查新旧 frame 差异并调用 `setNeedsLayout`，即使值相同也会触发 UIKit 的布局失效机制。

### 修复项 3（可选）：同步修正 `canBeReused` 语义

**当前代码没有问题**，但语义值得确认：

```objc
// hook_SysCell_canBeReused — L51-54
static BOOL hook_SysCell_canBeReused(id self, SEL _cmd) {
    if (purifyReadConfig(@"HideRevokeHint")) return YES;
    return ((BOOL (*)(id, SEL))_orig_SysCell_canBeReused)(self, _cmd);
}
```

`canBeReused` 返回 `YES` 告诉 TableView：这个 Cell 可以被复用/回收。因为 Cell 已经被隐藏且零高度，允许复用是正确的行为。微信优化同样返回 `YES`。

## 五、完整修复对照表

| Hook | 原代码 | 修复代码 | 原因 |
|---|---|---|---|
| `hook_SysVM_measure` | `CGSizeMake(size.width, CGFLOAT_MIN)` | `CGSizeZero` | `CGFLOAT_MIN` 导致 TableView 累加微量误差 |
| `hook_PatVM_measure` | `CGSizeMake(size.width, CGFLOAT_MIN)` | `CGSizeZero` | 同上 |
| `hook_SysCell_initWithViewModel` | 无 `setFrame:` | `v.frame = v.frame` | 缺 UIKit 布局失效标记 |
| `hook_PatCell_initWithViewModel` | 无 `setFrame:` | `v.frame = v.frame` | 同上 |

## 六、验证方法

修复后，按以下步骤验证：

```
1. 进入聊天页（消息多的聊天）
2. 快速滚动列表，确认无异常跳动
3. 开启「隐藏撤回消息提示」
4. 让好友发一条消息后撤回
5. 观察：撤回提示消失，且周围消息位置不变 ✓
6. 快速来回滚动，确认无偏移 ✓
7. 开启「隐藏拍一拍提示」
8. 让好友拍一拍
9. 观察：拍一拍提示消失，布局正常 ✓
10. 同时开启两个开关，重复测试 ✓
```

如果修复后仍有个别 Cell 偏移，检查 `CommonMessageCellView` 等父类是否也对隐藏的 Cell 做了额外布局处理。
