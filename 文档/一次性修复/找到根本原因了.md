# 找到根本原因了！

## 核心发现

微信优化的通讯录**只有一个 cell 类型**被处理圆角，而 MioPlugin 处理了**所有 MMTableViewCell**。

---

## 证据：微信优化的判断逻辑

### Line 11817-11819
```c
auVar26 = FUN_000c9d60(lVar9);  // auVar26 = [tableView numberOfSections]
lVar13 = FUN_000c82c0(uVar11,auVar26._8_8_,auVar26._0_8_);  // lVar13 = 当前 cell 的 row 索引
if (iVar4 == 0) {  // iVar4 = 0 表示 NOT 通讯录
    // 处理其他页面
}
else {  // iVar4 != 0 表示是通讯录
    // 进入通讯录专用逻辑
}
```

### Line 11834-11862：通讯录首行/中间行/末行判断
```c
lVar14 = FUN_000c97c0(lVar9);  // lVar14 = 当前 cell 的 row 索引
if (lVar14 == 0) {
    // 首行 → 顶角
}
auVar26 = FUN_000c97c0(lVar9);
if (auVar26._0_8_ != lVar13 + -1) {  // 不是末行
    // 中间行 → 无角
}
```

**关键**：`FUN_000c97c0(lVar9)` 获取的是**当前 cell 在整个 section 中的 row 索引**，而不是在整个 tableView 中的位置！

### 微信优化的逻辑

- Row 7（企业微信）→ 底角
- **整个 Section 0 看起来是一个完整卡片**

## 根因：微信通讯录的 Section 结构

### 微信通讯录的真实 Section 结构

```
Section 0: [新朋友, 仅聊天的朋友，群聊，标签] → 4 行
Section 1: [公众号, 服务号，企业微信联系人] → 3 行
Section 2: [我的企业] → 3 行（有 header "我的企业"）
Section 3: [A] → N 行（有 header "A"）
...
Section N: [Z] → N 行
```

### 微信优化的处理

微信优化在 `numberOfSections > 3` 时直接降级 per-section：
```
Section 0: 4 行 → per-section（顶角 + 底角）
Section 1: 3 行 → per-section（顶角 + 底角）
Section 2: 3 行 → per-section（顶角 + 底角）
```

**但图 1 显示 Section 0 的 4 行和 Section 1 的 3 行是连在一起的！**

这说明：**微信优化看到的 Section 结构和我们不一样！**
